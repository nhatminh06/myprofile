High Availability Is Not Recovery

A PostgreSQL replica is designed to reproduce the primary's history. That includes a perfectly valid DELETE that removed the wrong rows.

This was the distinction I wanted PgSentry to make concrete. Patroni, etcd, streaming replication, and HAProxy can keep a database endpoint available through node failure. None of them create an earlier version of data after a bad write has replicated everywhere.

Failover answers a different question

Patroni coordinates leadership while etcd provides quorum-backed cluster state. HAProxy routes clients according to node role. When a primary disappears, the system asks which replica can safely become writable.

Recovery asks: which point in history should exist? The latest replica is often the wrong source for that job because it contains the same destructive transaction.

Durability has a cost

PgSentry experiments with asynchronous and synchronous replication rather than treating them as labels. Asynchronous mode permits an acknowledged commit that has not reached a standby. Synchronous mode can wait for stronger evidence, but makes write availability depend on the configured acknowledgements.

A network partition makes the trade-off visible. The correct configuration depends on which loss and which outage the system is allowed to accept. “Automatic failover” does not settle that policy.

History lives in backups and WAL

The recovery path starts with a base backup and replays archived write-ahead log toward a chosen target. That is point-in-time recovery: reconstructing a database state before the destructive transaction, separately from the still-running HA cluster.

The separate restore matters. Overwriting the only available cluster before validating the recovered state would turn a data incident into a recovery incident. PgSentry keeps operational evidence around backup creation, WAL availability, restore, and verification.

The assumption that changed

I used to group replication, failover, and backup under one broad idea of database reliability. They protect against different failures.

replication: keep another current copy
failover: choose a writable survivor
backup + WAL: reconstruct an earlier history

A replica helps when a machine fails. It may be useless when the latest state is the failure. High availability reduces interruption; recovery changes history deliberately. A database design needs both questions answered.
