# 1. PRIMARY RULE: THIS IS A CONTENT-FIRST PORTFOLIO

The main purpose of this repository is to communicate:

* What Minh has built.
* What Minh has worked on.
* What Minh learned.
* What technical problems Minh can solve.
* What engineering areas Minh is interested in.

The main task when updating this repository is usually:

```text
UPDATE CONTENT
NOT
REDESIGN WEBSITE
```

Do not treat every portfolio update as an opportunity to create a new visual design.

The existing visual identity is intentional.

Preserve it.

# 3. PRESERVE THE EXISTING STYLE

Before changing UI code:

1. Inspect the current HTML.
2. Inspect the current CSS.
3. Inspect existing layout patterns.
4. Reuse existing classes.
5. Reuse existing spacing.
6. Reuse existing cards.
7. Reuse existing typography.
8. Reuse existing colors.
9. Reuse existing buttons.
10. Reuse existing responsive behavior.

Prefer:

```text

```

over:

```text
new component + new styling
```

A user should not be able to look at the page and immediately tell which section was generated by a coding agent.

---

# 4. VISUAL CHANGES MUST HAVE A REASON

A visual change is allowed only when it fixes one of these problems:

* Poor readability.
* Broken responsive layout.
* Overflow.
* Inconsistent spacing.
* Inaccessible contrast.
* Broken navigation.
* Missing mobile behavior.
* An existing component cannot accommodate new content.
* Information hierarchy is genuinely unclear.

Even then:

```text
MAKE THE SMALLEST CHANGE THAT SOLVES THE PROBLEM
```

Do not perform unrelated visual cleanup.

Do not "modernize" things just because you can.

# 7. DO NOT WRITE LIKE A RESUME EVERYWHERE

The portfolio is not simply an expanded resume.

Project descriptions should explain:

* Why the project exists.
* What makes it technically interesting.
* What architecture was chosen.
* What failed.
* What trade-off mattered.
* What was learned.

Do not turn every paragraph into:

```text

```

Use resume-style bullets only where appropriate:

* Experience cards.
* Compact project summaries.
* Skill sections.

Blog posts should read like engineering writing, not résumé bullets.

# 8. DO NOT INVENT METRICS

Never introduce a number unless it is verified.

Examples:

```text
30 ms
55 tests
16 dbt tests
9 VMs
99%
80%
5 services
12 ArgoCD Applications
4 Kyverno policies
```

Before publishing a number:

1. Inspect the current source repository.
2. Find the evidence.
3. Confirm the value is still current.
4. Confirm the meaning of the metric.
5. Confirm the project documentation uses the same definition.

If uncertain:

REMOVE THE NUMBER.

Prefer:

```text
Added extensive deterministic data-quality tests.
```

over an unverified:

```text
Added 55 tests.
```

Never invent:

* Latency.
* Throughput.
* Accuracy.
* Cost savings.
* Time savings.
* Scale.
* User count.
* Deployment size.
* Coverage.
* Performance improvements.


# 18. BLOG VOICE

Use first person where natural:

```text
I initially assumed...
I found...
I expected...
I broke...
I changed...
I measured...
I decided...
```

Technical humility is good.

Examples:

```text
I originally treated Kafka delivery as if every message would arrive
once. That assumption lasted until I started testing redelivery.
```

```text
My first README claimed a performance improvement before I had a
repeatable benchmark. I removed the number and built the benchmark
harness first.
```

```text
The kernel compiled, but QEMU immediately crashed with an illegal
instruction. The problem turned out not to be the kernel code itself.
```

This is much stronger than marketing copy.
